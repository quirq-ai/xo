xo: one package, a CLI and its server

The command line for XO Cloud's core API. The same Python package runs on your machine as xo and on Vercel as the xo server, which holds the Clerk Secret Key so the CLI never needs it. Standard library only. It also keeps your projects and spaces in your own Clerk metadata, lets you share a space or project with another user as an invite they accept or reject, and installs those projects on your machine and keeps them in step. Every command has its own diagram in section 03. Left out: test internals, the redaction rules in detail, and the Vercel deploy steps (see docs/).

01System context

The CLI sends your XO key to exactly one address, the xo server. The server answers account questions and writes your lists itself through Clerk (and, when you share, an invite in the other user's shared), and passes space creates and reads on to XO's core API with your key as sent. GitHub is reached through gh and its own login; projects are cloned with your own git.

02Commands: how argv becomes a request

Most commands are not written by hand. commands.register() reads the bundled OpenAPI spec and makes one command per operation, with every parameter and body field as a flag. A handful of built-ins sit beside them.

/user-metadata (no xo command)

xo has no command for it since xo me covers your own profile. The server's admin-only route stays as it was: GET and PATCH /user-metadata/{userId}, 20 a minute per key, a key with the xo_admin claim whose id is in XO_ADMIN_KEY_IDS, allow-listed keys only, one audit line per request. Admin needs two locks, and none is issued yet: until a key has the claim and its id is listed, every caller gets 403. PATCH changes only top-level keys named in XO_EDITABLE_*_KEYS.

04The server

Two front doors share one App. Every answer uses the core API's envelope, {"success", "data" | "error"}, and every request is counted for the public status page.

05Projects, spaces and invites in your metadata

A normal key changes three keys of Clerk private metadata. On its own user it writes projects and spaces, and shared when it accepts or rejects an invite; accept writes shared, projects and spaces in one merge. The one write to another user is a share: POST /me/share adds the caller's invite to the recipient's shared, and writes nothing else of theirs. The client never sends metadata: it sends a name, a kind, an id, a project and ref, an item and username, or an invite id, and the server builds the change. Every write goes through one engine, App._change() and App._change_keys().

06Install, update and sync

These put a space on your machine and write your changes back. A new workspace.py drives gitops.py; the metadata is only ever changed by the server, through PUT /me/spaces/{name}.

  • Branches move before refs are recorded. update pushes each tracked branch first; sync rebases each on its upstream and pushes it, undoing a rebase that conflicts. Tags and commits stay where they are.
  • Single projects: look up, then git. xo looks P up in your projects (GET /me/projects); xo install project:P then clones, or fetches and fast-forwards, ./REPO; update pushes its branch, never forced; sync runs pull --rebase, then that push. An existing checkout is used only if its origin is P's repo.
  • Your git, locked down. Every call sets GIT_ALLOW_PROTOCOL=https, turns submodules off, puts --end-of-options before any name or ref, and drops XO, Clerk and gh tokens from git's environment. xo never reads a git credential.
  • A narrow race remains. Two updates on different instances that both read rev N within the 0.3 s settle can both get 200; the later write stands, and the other client's next update is refused because the space no longer holds its base. If a stale write sends the rev backwards, xo sync stops and names the projects that differ.

07Access model

  • One network door per side. client.py is the only CLI code that talks to XO; gitops.py runs git and github.py runs gh. Clerk and Core in server.py are the only server code that talks out.
  • Keys are never printed. The key is redacted from every response and error, in its URL, JSON and HTML escaped forms too. Plain http:// is refused except to this machine.
  • Your own metadata is readable. /me returns your email and both metadata buckets, with values under credential-like names (or that look like keys) masked to their last 4 characters or (hidden). XO_ME_PRIVATE_KEYS can narrow which private keys it shows.
  • Three keys are writable by you, and one key of anyone else's. A normal key writes only projects, spaces and shared on its own user (accept writes all three in one merge), and on another user only its own invite in their shared (xo share). Every change is one audit line (a count, never a value; a share names the recipient only by a hash).
  • Admin is two locks. A Clerk API key with the claim xo_admin: true and an id listed in XO_ADMIN_KEY_IDS. None is issued yet, so /user-metadata answers 403 to everyone.

08Where state lives

No database. Your lists and the invites waiting on you live in Clerk; the CLI keeps two small config files and a state file per installed space; the server keeps everything else in process memory, so on Vercel each instance starts empty.
